# Phase 5B Story Intelligence S2: the AI writing assistant

> Current script → instruction → **Story Revision Proposal** → diff / review → **Accept** → a new script revision.
> Prism proposes the writing; the creator decides what becomes canon. The old revision always stays available.

S2 branches from `phase-5b-story-intelligence` at `78d12fa` (S1 merged). Everything is local / test only: migration
0055 is not applied to hosted DEV, and the Story worker login is not provisioned there.

## 0. First: the Story worker login (closes the S1 gap)

Migration 0054 creates `prism_story_worker` NOLOGIN without a password. S2 adds the same mechanism the generation and
continuity workers use.

```text
# admin shell, once per environment; the secret is generated by you, never committed, never printed
PRISM_STUDIO_STORY_DB_PASSWORD=<generated, 24+ chars> npm run story:db:provision            # enable LOGIN
PRISM_STUDIO_STORY_DB_PASSWORD=<new secret>           npm run story:db:provision -- --rotate # replace it
```

- `scripts/story-db-provision.mts` (logic in `scripts/lib/story-worker-role.ts`) is the ONLY place a secret is
  attached to the role.
- It refuses a short secret, a missing role, or a role with elevated attributes.
- It is idempotent: an existing login is left alone unless `--rotate` is passed.
- The ALTER ROLE statement is built server-side with `format(%L)`, so the secret travels only as a bind parameter.
- After provisioning it audits the role:
  - no superuser, BYPASSRLS, CREATEROLE, CREATEDB or REPLICATION;
  - NOINHERIT, with no memberships;
  - SELECT only on `story_proposals` and `writing_proposals`, and UPDATE only on their result and lease columns.
- The resulting URL goes on the **Story worker host only**: `PRISM_STUDIO_STORY_WORKER_DB_URL`. It never goes in the
  web app or in a `NEXT_PUBLIC_*` variable. The pooler login name is `prism_story_worker.<project ref>`.

`scripts/db-story-worker-login.mts` proves this on the disposable database:

1. Provision with a secret generated in-process; check that a second run is a no-op and that `--rotate` works (the old
   secret stops authenticating).
2. Log in genuinely as the worker: `current_user = session_user = prism_story_worker`.
3. Check it can read both proposal tables and cannot read Characters, Episodes, Scenes, script revisions, sessions,
   Assets or Projects; and cannot insert, delete, create, or SET ROLE.
4. Run the full audit.
5. Run `scripts/story-worker.mts --once` on the provisioned login, check the output never contains the secret, and
   check the worker refuses to start without its credential.

## 1. Architecture

```text
Write page (web) ─ Ask Prism ─▶ writing_proposals (frozen input) ◀─claim─ Story worker ─▶ provider.write()
        ▲                                                                                ├─ OpenAIStoryProvider
        └── Accept ─▶ script_revisions (immutable) + episodes.script_text + structure sync ├─ (Claude: same interface)
                                                                                         └─ FakeStoryProvider (free)
```

The S1 interface gains one provider-neutral operation, `write(WritingRequest) → WritingResult`, whose `operation`
covers the conceptual calls:

| Conceptual call       | `operation`  | Modes                                                    |
| --------------------- | ------------ | -------------------------------------------------------- |
| `rewriteStoryRange`   | `rewrite`    | Ask Prism, Rewrite, Dialogue pass, Tone, Shorten, Expand |
| `continueStory`       | `continue`   | Continue                                                 |
| `brainstormStory`     | `brainstorm` | Brainstorm                                               |
| `reviseStoryProposal` | `revise`     | Revise again (a DRAFT version plus a new instruction)    |

Inputs and outputs are Prism domain types only. No vendor shape crosses the interface.

**OpenAI** reuses S1's adapter: the same transport, pinned SDK, `store: false`, strict JSON schema and two-call
contract (answer plus at most one correction turn). Timeouts are ambiguous and never re-sent. Calls use the writing
schema `WRITING_JSON_SCHEMA` and prompt `story-writer-v1`.

**The Story worker** claims writing proposals as well as Production Proposals. It re-checks the spend gate against the
frozen estimate and confirmation, calls `write`, validates the answer (`validateWriting`) and writes the result once.
It reads only the frozen row and never writes a screenplay. Memory mode runs the same loop in-process.

## 2. The writing workspace (Episode → **Write**)

- **Left: the screenplay.**
  - Scene chips; a `●` marks a story-changed Scene.
  - The Scene (or whole Episode) as selectable read-only text.
  - The screenplay history.
- **Right: the Prism AI conversation.**
  - Each turn shows the creator's instruction (with its mode and scope) and Prism's answer.
  - The Ask box has a free-form instruction plus presets: Ask Prism, Rewrite, Continue, Shorten, Expand, Improve
    Dialogue, Change Tone, Increase Tension, Make Funnier, Brainstorm.
  - Scope: Selection / This Scene / Whole Episode, and the number of versions.
  - No production fields.

**Targets:**

- A selection is sent as offsets plus the selected text; the server verifies both against the current screenplay.
- A Scene is located with the same stable-id sync the Script page uses.
- The Episode scope is limited to 120k characters. Scene-sized requests send only the Scene and its neighbours.

**Plain-language parsing:** "three versions" → 3 alternatives; "Give me five ways to…" → a 5-idea brainstorm.

**Conversation:** each turn freezes the last six turns (instruction, Prism's reply, the chosen text). "Version 2, but
warmer at the end" works without restating the Scene.

## 3. Story Revision Proposals and script versioning (migration 0055)

**Audit result:** there was no script history. "Save & sync structure" overwrote `episodes.script_text`. S2 keeps
`episodes.script_text` as the canonical screenplay (everything downstream already reads it) and adds the smallest
history:

| Table                 | Purpose                                                                                                                                                                                                                                                     |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `script_revisions`    | insert-only history: `baseline` (the text before history began), `import` (S1's original imported source, linked to its Story proposal), `creator_edit`, `ai_revision` (the proposal and version accepted, the lines written), `restore`; changed Scene ids |
| `writing_sessions`    | one conversation on an Episode, plus its optional capped spend allowance (`budget_usd`, `reserved_usd` never decreasing, `budget_expires_at`)                                                                                                               |
| `writing_proposals`   | one row per turn, as below                                                                                                                                                                                                                                  |
| `scene_story_changes` | "Story changed after production breakdown" markers; only `reviewed_at` changes, once                                                                                                                                                                        |

Each `writing_proposals` row records:

- **Frozen input:** project, Episode, session and turn, parent (with the revised version), mode, scope and range,
  instruction, base fingerprint and revision, target text, draft, frozen textual context, provider, model, schema and
  prompt version, estimate, confirmation and spend authorization.
- **Result, written once by the worker:** message, alternatives (text, explanation, implied Character facts) or ideas,
  plus usage, cost, calls and error.
- **The creator's decision:** accepted version and revision, or rejected; plus bookmarks.

Owner-only RLS, no delete policies, and triggers enforce the same rules in the database as in the memory twin:

- a frozen input;
- a write-once result;
- final decisions;
- immutable revisions;
- same-project and same-Episode references;
- a brainstorm can never be accepted;
- the worker can neither decide nor read anything else.

**Accept**, in one transaction:

1. The baseline revision, if the Episode has none.
2. The new `ai_revision`.
3. The Scene markers.
4. `ready → accepted`.

Then the structure syncs exactly like a Script-page save. Accept is refused if:

- the screenplay changed since the proposal was written (base fingerprint);
- the version would change the Episode's scene headings;
- the proposal was already decided.

A manual Script-page save is also recorded (`creator_edit`). **Restore** writes a new revision with the old text.
History is never rewritten.

## 4. Review: diff, alternatives, brainstorm

- **Diff:** Original vs Proposed. Line-level LCS, word-level highlights inside changed lines, character-level for
  Japanese. A line and character count is shown, and a side-by-side view is available.
- **Actions** per version: Accept version X, Save as alternate (a bookmark, never canon), Copy, and Revise again (a new
  proposal from that version). The proposal as a whole can be Rejected. Ready proposals are labelled
  "AI suggestion — not canon".
- **Multiple options:** "Give me 3 versions" renders Version A, B and C. Nothing becomes a revision until one is
  accepted.
- **Brainstorm** returns ideas only, with no text to accept, and never changes the screenplay or production records.
  "Write this idea" turns a chosen idea into a revision proposal for the same target.
- **Implied Character facts** are shown on the version as "kept in this revision only — not saved to the Character".
  Character records change only when the creator edits them.

## 5. Canon, staleness and traceability

- **Canon:** only accepted text is in `episodes.script_text`. Story Intelligence analysis of an Episode script, the
  Scene breakdown, Shot planning and Production Frame story context all read it. Rejected or unaccepted suggestions
  live only in `writing_proposals`.
- **Staleness:** after Accept (or a manual edit or restore), every existing Scene whose block text changed is recorded
  on the revision. Those with breakdown (Shots or a written summary) get a marker:
  - The Write page and the Shot page show "Story changed after production breakdown", with **Mark breakdown
    reviewed**.
  - Nothing is deleted or rewritten automatically (S3/S4 may reconcile).
- **Traceability:**
  - An Episode created by S1 Apply starts its history with the `import` revision, linked to its Story proposal (and
    file). S1 citations keep reading the proposal's frozen source text.
  - Creator-approved AI revisions are separate `ai_revision` rows naming the proposal, the version and the lines
    written. They are never presented as words from the uploaded screenplay.

## 6. Prompt context and safety

- **Context** (frozen on the proposal, textual only, never images):
  - project and Episode; synopsis; genre and tone;
  - the Scene's heading, summary, purpose and emotions;
  - the Characters present, speaking or named: role, description, personality, voice (behaviour and signature
    behaviour), relationships;
  - the whole Scene around a selection, plus the text just before and after;
  - the recent turns.
- **Isolation:**
  - The instructions are static.
  - The creator's instruction, the context, the draft and the target are separate delimited blocks.
  - Content can never close a block early (`<<<` and `>>>` are escaped).
  - The schema is strict and Prism re-validates the answer.
  - Dialogue such as "Ignore previous instructions" stays dialogue.

## 7. Cost: bounded writing sessions

- Every request has an estimate: a ceiling of input tokens plus this request's output budget. The output budget scales
  with the target and the number of versions, never the model maximum.
- Paid Prism AI stays off unless `PRISM_STUDIO_ALLOW_PAID_STORY_AI=true`, and the per-request ceiling
  `PRISM_STUDIO_STORY_AI_MAX_USD` still applies.
- A paid request goes ahead only with:
  - **an explicit confirmation:** type the estimate in "Confirm total" (S1's pattern); or
  - **a capped session:** the creator allows up to $X (at most `PRISM_STUDIO_STORY_AI_SESSION_MAX_USD`, default
    $1.00) for 1–4 hours on this conversation.
- Under a capped session, each request's estimate is reserved atomically against the allowance. The reservation never
  decreases, so it can never be exceeded. The worker still re-checks every request.
- Spend is never unlimited.

## 8. The FIRST real Story Intelligence call: owner acceptance (NOT executed)

This is prepared and documented; it must not be run without the owner's separate authorization.

| Setting    | Value                                                                                                        |
| ---------- | ------------------------------------------------------------------------------------------------------------ |
| Target     | Ojou-sama Episode 1, Scene 6 (`INT. SKY-VIEW RESTAURANT - NIGHT`), 7 lines                                   |
| Model      | OpenAI `gpt-6-luna` ($0.10 / 1M input, $0.50 / 1M output)                                                    |
| Request    | "Make Yumeko more guarded and emotionally restrained without changing what happens in the scene.", 1 version |
| Estimate   | **$0.0014** (≈ 2,900 input tokens, ≤ 2,162 output tokens), the figure Prism shows                            |
| Worst case | ≈ **$0.003**, if the single correction turn also runs                                                        |
| Cap        | `PRISM_STUDIO_STORY_AI_MAX_USD=0.01`; no session allowance                                                   |

Steps, on a local or disposable environment:

1. Apply migrations through 0055 to the target database, and provision the worker login (§0).
2. Web: `PRISM_STUDIO_ALLOW_PAID_STORY_AI=true PRISM_STUDIO_STORY_AI_MAX_USD=0.01`.
3. Story worker host only: the same two, plus `PRISM_STUDIO_PROVIDER_OPENAI_STORY_API_KEY=<key>` and
   `PRISM_STUDIO_STORY_WORKER_DB_URL=<provisioned login>`. Then run `npm run worker:story -- --once` after queuing.
4. Write → Scene 6 → This Scene → type the instruction → Advanced → Model **GPT-6 Luna** → Ask Prism.
5. Prism refuses and shows the estimate: "Estimated cost: $0.0014 … Enter 0.0014 in "Confirm total"". Enter `0.0014`
   in Confirm total and click Ask Prism again.
6. Run the worker once. Check Advanced on the turn: provider `openai`, model `gpt-6-luna`, prompt `story-writer-v1`,
   calls 1 (or 2), and an actual cost of at most $0.01.
7. Review the diff; Accept or Reject. Either way the old screenplay remains in the history.
