# Candidate sets (Phase 2E)

A **candidate set** is an intentional comparison experiment for ONE shot: the same production truth sent to several
models, each as its own attempt and job.

```
SHOT PREP → pick models → CANDIDATE SET → N × (GenerationAttempt + GenerationJob) → compare → human review
          → Best → (explicit) Promote to Shot
```

## What is frozen

The set stores `packageFingerprint` (the single production package every candidate was built from), the server
ceiling that applied, the estimated total, and the recommendation shown at creation (engine version, profile, scores,
what was recommended vs what was chosen: product data, never a nag). Each **member** freezes its model, input mode,
resolution tier, native-audio flag, estimate and a plan (adaptations, what it would receive, pricing version).

Intent is shared; execution is not: **Production package: same · Provider adaptation: per model · Provider request:
per model.** The set page lists _Same for every candidate_ and _Necessarily different_ (ratio, generated duration,
references used, start frame as exact first frame, performed audio, tier, provider audio, input mode, model-specific
prompt wording). It never claims identical conditions.

## Creating and paying

1. Tick models in the matrix. **Nothing is generated by ticking.**
2. The panel shows each estimate, the candidate count and the **maximum total**.
3. Paid candidates need: `PRISM_STUDIO_ALLOW_PAID_GENERATION`, the per-generation ceiling
   (`PRISM_STUDIO_MAX_GENERATION_USD`) for every candidate, **and** the set ceiling
   `PRISM_STUDIO_MAX_CANDIDATE_SET_USD` (unset ⇒ paid sets are blocked). `PRISM_STUDIO_MAX_CANDIDATES_PER_SET`
   (default 6, max 8) bounds the set.
4. The user acknowledges what each candidate will not use, and confirms the displayed maximum. The server recomputes
   the total and **refuses a mismatch**; a client can never raise a ceiling.
5. Free (mock) sets need none of the paid gate. No automatic or overnight paid benchmarking exists.

## Execution and isolation

The set is created first (members `planned`); then each candidate goes through the normal
`prepareSubmission → createAttemptWithJob`, with a deterministic idempotency key per (set, position, package, model).
A candidate that cannot be submitted is recorded on its member (`submit_state = failed`) and the others still run.
Runtime failures are isolated by construction (separate jobs): the rollup reads e.g. `2/3 completed, 1 failed` and
the comparison works for the successful outputs. Same-shot concurrency is allowed for sets only
(`CreateAttemptInput.allowConcurrentOnShot`); the project-wide active limit still applies.

## Winner and promotion

- **⭐ Best** marks the set's single preferred candidate and records a positive review. It changes nothing about the
  shot.
- **Promote to Shot** is a separate, confirmed step: it is the existing creative approval of that attempt (which
  supersedes the shot's previously approved attempt, history intact) plus a record on the set. Losing candidates are
  never deleted; they are training data.

## Production Frame candidate sets (Phase 2G.2)

The same sets, tables and review workflow; no second candidate table. A set made of still images for the Shot's Production
Frame carries `generationPurpose: "production_frame"` in its frozen recommendation JSON (and in every member's plan), and each
attempt's immutable request carries `purpose: "production_frame"`. Such a set is an **image review surface** (large stills,
no playback controls, modality-aware copy) and offers **Use as Production Frame** instead of **Promote to Shot**. ⭐ Best is the
experiment's preference; **CURRENT PRODUCTION FRAME** (derived from the selected frame's source attempt) is the Shot's canonical
visual; they are independent. One candidate is one attempt is one image. Image reviews feed the model history only for the same
purpose. See [image-shot-generator](image-shot-generator.md).

## Backward compatibility

Existing attempts are untouched. An attempt outside any set is labelled **Standalone generation**; no candidate history
is fabricated.

## Persistence

Migration `0026`: `generation_candidate_sets`, `generation_candidate_members`, `generation_reviews`,
`generation_candidate_events`. Triggers: a set's identity/package are frozen; a preferred/promoted attempt must be a
member (promotion needs a succeeded attempt); members are frozen apart from their one-time attempt link. See
[security-model](security-model.md). Verified by `npm run db:candidates`.

## The first real set (executed 2026-10-14) and what it taught

One candidate set ran on the disposable `runway-smoke-test` fixture (a **benchmark project**, see below): Gen-4.5,
Gen-4 Turbo and Hailuo 3 (768p), 2 s, one shared package fingerprint
(`bea62422…959b0f`), estimated $0.56.

| Candidate   | Outcome                                                                            | Actual  |
| ----------- | ---------------------------------------------------------------------------------- | ------- |
| Gen-4.5     | succeeded, ingested (generation 68 s, total 159 s)                                 | $0.24   |
| Gen-4 Turbo | accepted by the provider, then `INTERNAL.BAD_OUTPUT.CODE01` (provider_unavailable) | unknown |
| Hailuo 3    | rejected at submission, HTTP 400 "Model does not support this input", never billed | none    |

Failure isolation held (1/3 completed, 2 failed; nothing retried or replaced). Lessons, now encoded:

- **Hailuo 3's range is 5–15 s** (API reference). The 2 s request was below the minimum and should never have been
  sent: the catalog recorded the bounds as unknown. Phase 2E.1 fixed the catalog, so a 2 s Hailuo is ADAPTATION REQUIRED
  (generate 5 s, trim to 2 s, priced at 5 s) or UNSUPPORTED, and never a native request.
- **Gen-4 Turbo's 2 s is valid** (2–10 s). Its failure was the provider's, and stays `provider_unavailable` in history.
  History is never rewritten when the catalog improves.
- A failed candidate has no clip, so it exposes **no** Good / Shortlist / Best controls and cannot be reviewed.

## Benchmark / fixture projects

`projects.purpose` (`production` | `benchmark` | `test`; migration 0029, which replaced the 0028 boolean) is an **explicit**
classification, never inferred from a slug. A benchmark or test
project's candidate sets, reviews, winners, costs and comparison UI all work normally, which is the point: they let the
tooling be exercised end to end. Its records are excluded from production model-performance aggregates and from routing
recommendations (`inScope()`), and every page that shows its data says **TEST / BENCHMARK DATA**. Classify an existing
fixture with `npm run runway:fixture -- --mark-benchmark` (new fixtures are created as benchmark projects).
